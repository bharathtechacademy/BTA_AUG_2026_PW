Story Title

Login Form Validations for basic Login with user credentials

User Story (Jira Requirement)

User Story

As an existing user, when I log in to my Creatio CRM account, I want to use my business email and password through a secure and well-designed form so that I can sign in and see clear errors when I enter invalid credentials.

Context

This issue is about validating the basic login form for Creatio CRM. It covers error handling for invalid email formats, overly long email values, overly long passwords, and invalid login credentials.

Acceptance Criteria

  • The Business Email field should be highlighted in red and show "Invalid email format" when the user enters an invalid email format or domain name.
  • The Business Email field should be highlighted in red and show "Invalid email format" when the user enters an email with more than 400 characters.
  • The Password field should be highlighted in red and show "Invalid value. Value must contain up to 100 characters" when the user enters a password with more than 100 characters.
  • "Invalid email or password" should be shown at the bottom of the page when the user enters an invalid username or password and tries to log in.

Requirement Understanding & Analysis

Business Objective

To implement comprehensive validation on the Creatio CRM login form that provides clear, user-friendly error messages for invalid inputs and protects the application from malformed data entry.

Functional Summary

  • Validate email format on the Business Email field
  • Enforce email character length limit (max 400 characters)
  • Enforce password character length limit (max 100 characters)
  • Display appropriate error messages for validation failures
  • Provide authentication error messaging for invalid credentials

Key Dependencies & Constraints

  • Email Validation Library: A robust email validation mechanism that recognizes valid RFC 5322 formats
  • Client-side vs Server-side: Validation should occur on both client (UI feedback) and server (security)
  • Error Message Display: UI must support red highlighting and clear error text placement
  • Backend Authentication: Server must validate credentials and return appropriate error responses
  • Security Considerations: Passwords must not be logged; validation errors must not reveal whether email exists

Things to be Taken Care of (Dev & Infrastructure)

  • Implement email validation regex or library that handles RFC 5322 compliance
  • Set up character limit enforcement in the form fields (400 for email, 100 for password)
  • Add CSS styling for error state (red border/highlight for invalid fields)
  • Create error message display container at the bottom of the login form
  • Implement server-side validation to reject oversized payloads
  • Ensure backend authentication service returns consistent error messages
  • Set up password field masking (bullets/asterisks)
  • Implement client-side form state management for error persistence

  • Password Validator Component: Function/component that validates password length

Test Plan

Objective

Validate that the Creatio CRM login form correctly implements all input validation rules and provides appropriate error messaging for invalid inputs and authentication failures.

Scope

In Scope:
  • Business Email field validation (format and length)
  • Password field validation (length)
  • Error message display and formatting
  • Login form visual states (error highlighting)
  • Authentication error messaging
  • Browser compatibility (Chrome, Firefox, Safari, Edge)
Out of Scope:
  • Password reset functionality
  • Account lockout after multiple failed attempts
  • Two-factor authentication
  • Password complexity rules (beyond length)
  • Backend performance testing

Risks & Assumptions

🔴 Risk (High): Validation not enforced on backend could allow oversized payloads to be submitted, causing application errors or security issues.
🟠 Risk (Medium): Email validation regex might not handle all edge cases (internationalized domains, subdomains), leading to false positives/negatives.
🟠 Risk (Medium): If error messages are too generic or inconsistent, users may not understand validation requirements.
⚪ Risk (Low): Visual styling of error state may not be accessible (color-only indication) for color-blind users.
Assumptions:
  • Login form HTML/template is already available for testing
  • Backend authentication service is functional and returns appropriate error codes
  • Email validation follows standard RFC 5322 format
  • Red highlighting for errors is the standard visual indicator
  • Testing environment has internet access for email verification services if needed

Test Strategy

Approach: Boundary value analysis, equivalence partitioning, and negative testing to validate all acceptance criteria.

  • Layer 1 - Unit Testing: Validator functions for email format and length rules
  • Layer 2 - UI/Integration Testing: Form field behavior, error display, highlighting
  • Layer 3 - End-to-End Testing: Complete login flow with valid/invalid credentials
  • Layer 4 - Accessibility/Browser Testing: Cross-browser and accessibility compliance
